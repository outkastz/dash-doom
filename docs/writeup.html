Getting DOOM to run on a Sony Dash

Sony Dash HID-C10, aka a Chumby with a Sigma Designs set-top chip inside. This is the log of putting id Software's DOOM on it — plus everything that stood in the way — written up as a blueprint for whoever's next.

The Dash ships two personalities on the same board: a locked-down Chumby/Sony "smart display" app platform, and underneath it, a bog-standard Sigma Designs SMP8654 set-top-box chip — the same silicon family that ran cable boxes and IPTV decoders in the mid-2000s. Everything below is what it took to get that chip to run a 1993 first-person shooter instead of a weather widget, and exactly where we got stuck.

Nothing here required opening the case or touching a chip with a probe. Every result below came from software running on the device itself, over the network, through the official recovery-flash mechanism.

01The platform

The Dash boots one of two root filesystems depending on a kernel command-line flag (rfsp=), read out of U-Boot environment variables that are themselves editable at runtime via setxenv:

FlagRootfsNormally reached byWhat runs there
rfsp=9rfs1 (sigmblk9, 64 MB)ordinary power-onThe real Sony/Chumby control panel. Sound hardware is fully initialized here.
rfsp=8rfs2 (sigmblk8, 30 MB)button-combo + power → "Special Options" recovery menuA minimal Flash-based recovery/unbrick UI, meant only for reflashing the device.

The two kernels living in flash (sigmblk6 and sigmblk7) turned out to be byte-identical — there is no separate "sound kernel." The audio difference between the two boot modes is entirely userspace: what each rootfs's startup scripts choose to initialize.

Both rootfs images are cramfs with a 16 KB block size (the MIPS kernel here runs 16 K pages, not the usual 4 K — this tripped up early attempts at surgical patching before we understood it).

02Escaping Flash — getting our own pixels on screen

The recovery UI is itself just a Flash movie (chumbyflashplayer.x playing a controlpanel.swf) that, conveniently, is told by a config file to preload a second SWF from the USB stick used to boot it:

# /mnt/usb/flashplayer.cfg
PreloadWidget /mnt/usb/unbrick.swf

That preloaded widget can shell out to a script we fully control (unbrick_async). From there the plan was straightforward: kill the Flash player, and draw the screen ourselves. The execution was not straightforward at all.

Dead end: the Linux framebuffer

The device exposes a normal-looking /dev/fb0 (800×480, RGB565, via an em8xxxfb.ko driver). Writing to it worked — for exactly one frame. After disassembling the driver, the reason became clear: the Sigma OSD compositor does not continuously scan the framebuffer. It only re-composites when a specific pair of hardware registers gets poked by fb_pan_display — and even calling that ourselves via FBIOPAN_DISPLAY was a no-op, because the OSD memory only ever holds one buffer's worth of pixels; there's no second buffer to pan to. Double-buffering the driver at the module level (insmod em8xxxfb.ko double_buffering=1 ...) allocated two buffers and let us pan between them — and the screen still didn't update. The fb0 device is a passive memory window; it is not what actually drives the panel.

Wall

Anything built on /dev/fb0 — mmap, write(), pan ioctls, double-buffering — is a dead end on this hardware. Don't repeat this path; the real compositor lives one layer up.

What actually drives the panel: Sigma's RM/DCC stack

The real path is Sigma's "Rich Media" userspace API — librua (Resource/Unified Access) and libdcc (Display Chain Composer) — the same stack the Flash player itself uses. None of the headers for this ship on the device (find mrua -name '*.h' returns nothing), but a community-maintained SDK for a sibling chip, jur/smp86xxsdk (written for the SMP8635), turned out to be ABI-compatible enough with our SMP8654 to use as a starting point once linked against the Dash's own .so files rather than the SDK's.

The working recipe, once found:

RUACreateInstance(&pRUA, 0)
DCCOpen(...)
// the critical call — see callout below
DCCInitMicroCodeEx(pDCC, DCCInitMode_InitDisplay)
DCCOpenMultiplePictureOSDVideoSource(profile, 2 /* buffers */, &pVS, 0)
// per frame:
RUALock / RUAMap(buffer[i]) → write RGB565 pixels → RUAUnLock
DCCInsertPictureInMultiplePictureOSDVideoSource(pVS, i, 0)  // flips 0↔1
Key finding

The SDK defaults to DCCInitMode_LeaveDisplay (leave the recovery UI's existing, non-DCC display setup alone). Under that mode, the call that routes a video source to the screen — DCCSetSurfaceSource — blocks forever inside the kernel, because it waits on a display-ready event that a non-DCC-owned display never fires. Switching to DCCInitMode_InitDisplay makes DCC take ownership of the whole display chain, the event fires, and everything downstream works immediately.

One more surprise once pixels were finally landing on the panel: colors were wrong — grays and browns rendered green, gold rendered blue. The OSD profile is configured as ColorFormat_16BPP_565 with ColorSpace_RGB_0_255, but the hardware composites those bits as YUV regardless of what the profile claims. The community SDK's own sample code has a resigned comment to this effect ("the color space seems to be YUV also when we specify RGB"). The fix was a 65,536-entry RGB565→YUV565 lookup table applied per pixel — one array index, negligible cost, and the picture snapped into correct color.

03Porting DOOM

With a real display path in hand, the game itself was the easy part. We used ozkl's doomgeneric (Techflash's linuxvt fork) and wrote a new backend, doomgeneric_dccdash.c, that does the DCC setup once at startup and, each frame, nearest-neighbor-upscales DOOM's native 320×200 buffer straight into whichever OSD buffer isn't currently on screen, then flips.

ItemDetail
ToolchainBootlin mips32el--glibc--stable-2020.02-2 (glibc 2.31 build, but with a pre-2.34 C runtime — produces binaries that only require GLIBC_2.7, matching the Dash's ancient glibc 2.8)
LinkingDynamically linked against the Dash's own librua/libdcc/libllad, not the SDK's stand-ins — needed to make the InitDisplay path work on real SMP8654 hardware
Resolution320×200 native, nearest-neighbor scaled to fill 800×480
InputTouchscreen (/dev/input/event0, evdev) and a UDP :5001 fallback for testing from a PC
Frame rate~40 fps measured

One bug worth flagging for anyone doing a similar port: doomgeneric's frame-drawing hook was calling RUALock/RUAMap fresh every single frame but only ever unlocking, never unmapping. The kernel's pool of mappable regions is finite — the game ran perfectly for about eleven seconds (title screen through the demo transition) and then segfaulted the instant the pool was exhausted. The fix is to map both OSD buffers exactly once at startup and hold those pointers for the process's lifetime, which is also just the more sensible design.

04The audio investigation

This is where most of the effort in this project went, and it's the one piece that remains unsolved. The short version: every layer of the digital audio pipeline works correctly, and no sound reaches the speaker. Here's the chain, traced end to end.

DOOM PCM data ↓ RUASendData() — confirmed: 49/49 sends accepted, decoder state = playing MRUA audio decoder (Sigma DSP, engine 0x1b) ↓ DCCSetAudioPcmxFormat() — confirmed OK, 44.1kHz/16-bit/stereo Audio engine → I2S output routing ↓ ✗ never configured — this is the wall External I2C audio codec (init/unmute over I2C confirmed working) ↓ Speaker

What we ruled in

  • The DSP audio microcode does load. Both boot modes run the same firmware-loading step (fw_reload → xlu_load_t3.bash) that loads and starts the audio DSP cores, using the correct region-specific microcode variant (_nodts, not _dts54 — the wrong variant returns a decrypt error rather than loading).
  • The decode pipeline genuinely runs. Opening a decoder source, setting PCM format, and streaming buffers all return success; the decoder's internal clock (STC) advances in real time exactly as expected; feeding buffers reports every one accepted.
  • The analog output hardware is alive. The I2C-attached audio codec initializes and unmutes cleanly (audioCodec i → "Audio codec init done — DVT board"), and toggling its mute produced an audible click through the speaker during testing — proof the codec, amp, and speaker are all physically connected and working.

What blocks it

Root cause

The recovery rootfs's kernel has no Linux sound core at all — CONFIG_SOUND is unset, and there is no soundcore.ko anywhere in the firmware, on either rootfs. em8xxxalsa.ko (the driver the real control panel uses) and em8xxxoss.ko both fail to load with Unknown symbol register_sound_dsp / snd_card_new — the symbols they need are simply absent from this kernel build.

That driver, when it does load (on the normal, production boot), is what performs the actual engine-to-I2S output routing — a sequence of roughly twenty undocumented property writes to the audio engine module that a userspace program has no other way to trigger. We disassembled enough of em8xxxalsa.ko to identify several of the relevant property IDs (4162 = master volume, 4168 sits earliest in the sequence, along with 4158/4160/4166/4186/4652), and confirmed we can call the same underlying API the driver uses (libaudiooutports.so's OutportsAudioApplyOptions, the code behind the set_outports CLI tool) — but the very first property write in that sequence blocks forever inside the kernel, in an uninterruptible wait state, when called this way. It's waiting for a piece of engine state that only the (missing) ALSA driver's own initialization would normally establish first.

In other words: this isn't a missing command-line flag or a wrong parameter. It's a genuine kernel capability the recovery environment doesn't have, gating a userspace API that has no fallback path around it.

What we tried and ruled out

  • Loading the audio ucode ourselves at a more favorable point in boot, before video ucode claims the DSP memory pool — unnecessary; both boot modes already load audio ucode successfully by the time our code runs.
  • Replicating the boot-time set_outports call that the normal boot's init_fb runs — succeeds (no error) but produces no sound, across seven different output-mode/clock configurations.
  • Driving a suspected mute GPIO directly — a real lead (register 0x10504 does change when the real control panel's audio starts playing) that turned out to be a status bit, not a controllable mute; writes to it didn't reproduce the effect.
  • Going through the Flash player's own media-playback path (chumby_client → libmediaplayer.so) instead of raw MRUA calls — the Flash player's own audio dispatch fails in the recovery environment too (BtPlayObject::GenericRequest dispatch failed), for the same underlying reason.

All of this is fully instrumented and independently reproducible: a webcam microphone pointed at the unit, captured and analyzed with an FFT/Goertzel tone detector, confirms silence (or a correctly detected tone, when one was actually reaching the speaker during earlier debugging) without needing anyone in the room.

05What we learned about the firmware's security model

Along the way we mapped out how this firmware actually protects itself, which matters for anyone thinking about further modification:

  • Firmware images are integrity-checked, not authenticated. The official updater protects u-boot/psp/k1/k2/rfs1/rfs2 with plain MD5 checksums — there's no cryptographic signature on any of them.
  • The one real signature on this device (a DSA key + a verify binary) only gates downloadable Flash content — widgets and control-panel SWFs — never the firmware itself.
  • U-Boot doesn't verify the rootfs at all. It just loads whichever kernel rfsp points at and boots it.
  • A single string decides "production" vs. "developer" behavior across every startup script we found (rcS, rcS.background, start_display_service.sh, start_control_panel): /etc/firmware_build_type. Only the literal values production/release or production/candidate take the locked path; anything else — including the file simply being unreadable — takes a developer branch that runs userhooks and, if a marker file is present, starts sshd with an empty root password.
Open discrepancy, not yet resolved

On paper, flipping that one file's value should be enough to get an interactive root shell on the sound-capable normal boot. In practice, every attempt to do this on real hardware — renaming the file so it can't be read, and separately, rebuilding the whole rootfs image with the value changed — causes the boot to loop before that check is ever reached, even though a rebuild that changes nothing reflashes and boots fine. Something earlier in boot is sensitive to the modification in a way we haven't isolated yet. See Open problems.

The practical upshot: the recovery rootfs (rfs2) is freely modifiable and reflashable — that's the whole reason this project was possible without hardware tools. The normal, sound-capable rootfs (rfs1) is where things get harder, for reasons that currently look like an implementation quirk rather than a real signing barrier.

To be precise about what "DOOM in normal boot mode" means here: the device's boot menu selection is written into U-Boot environment variables, which we can edit live. Pointing the normal power-on path at the recovery kernel+rootfs pair means the device powers on straight into DOOM with no button combo — from the user's chair, that is normal boot. It is not, technically, the same rootfs that has working sound hardware. Closing that gap is exactly the open problem in §05 and §08.

07The blueprint — reusing this on other Sigma-based boxes

The Dash is not unique silicon. The SMP865x/86xx family shipped inside a lot of early-2010s IPTV set-top boxes and smart-display products. If you're staring at one of those, the general shape of this approach should transfer:

  1. Find an unsigned, writable code-execution foothold first. Ours was a recovery/unbrick UI that preloads a script off USB — look for the equivalent on your device (recovery menus, diagnostic modes, and "rooted" community firmware zips are the usual places).
  2. Don't trust the Linux framebuffer device. If there's a real hardware compositor (OSD, display chain, whatever the vendor calls it) sitting between the fb device and the panel, writes to /dev/fb* may only ever show the first frame. Check for a vendor userspace media API (Sigma's is librua/libdcc; other SoC vendors have their own) before spending days debugging fb ioctls.
  3. Community SDKs for a sibling chip are worth trying even off-target. The jur/smp86xxsdk project targets a different (but related) Sigma part than ours and still got us headers, structs, and working call sequences — the ABI overlap between chips in the same family is often good enough to bootstrap from, especially once you link against the target device's own shared libraries instead of the SDK's.
  4. Trace security boundaries empirically, not just by reading scripts. Our biggest surprise was that a check that looks trivially bypassable on paper (a single string comparison) doesn't behave that way on real hardware once you actually try it — see §05. Read the scripts to find where to look, but verify on the device before declaring something solved.
  5. Instrument your verification, especially for anything analog (audio, in our case). A microphone plus an FFT tone detector meant every audio experiment could be checked automatically, without needing a person in the room to listen — this alone was worth doing early.

08Open problems — where we could use help

Two concrete, well-bounded problems remain, both documented above in enough detail to pick up without redoing the legwork:

  • Audio output routing without a sound core. We need either (a) the missing kernel sound-core symbols made available in the recovery environment somehow, or (b) the specific sequence of RM engine properties em8xxxalsa.ko sets before its first (blocking) output-routing write, so it can be replicated from userspace in the right order. Anyone with SMP86xx ALSA driver source or a debugger on similar hardware would make short work of this.
  • Why a value-only rootfs modification loops the normal boot. Static analysis of the boot scripts says changing one file's contents should be harmless past a certain point in boot; live testing says otherwise, twice, by two different methods. If you've dealt with cramfs-based embedded Linux boot loops before and have a diagnostic technique we haven't tried, this is the one blocker standing between "DOOM with no caveats" and where we are now.

Everything referenced in this report — the DOOM binary, the DCC display backend, the audio test tools, and the deploy scripts — is packaged for anyone who wants to reproduce or continue this on their own unit.
